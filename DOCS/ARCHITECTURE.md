# ARCHITECTURE.md

## 1. 아키텍처 목표

ALOHA Slide Studio는 초기에는 브라우저 안에서 독립적으로 동작하는 Local-first 애플리케이션입니다. 슬라이드 데이터 모델을 중심에 두고 편집기, 발표 모드, 저장소, 내보내기 기능이 이를 공유하도록 구성합니다.

핵심 원칙은 다음과 같습니다.

- UI 컴포넌트가 저장소나 파일 변환 세부 구현에 직접 의존하지 않습니다.
- 캔버스는 슬라이드 데이터를 렌더링하고, 편집 동작은 별도 상태/명령 계층에서 처리합니다.
- 편집 화면과 발표 화면은 가능한 한 동일한 요소 렌더러를 공유합니다.
- 저장 형식과 내보내기 형식은 분리합니다.
- 데이터 모델 변경은 `schemaVersion`과 마이그레이션을 통해 관리합니다.

## 3. 프런트엔드 레이어

### App Layer

앱 초기화, 라우팅, 전역 Provider, 오류 경계 등을 담당합니다. 비즈니스 규칙을 넣지 않고 기능 모듈을 조합합니다.

### Feature Layer

사용자 기능 단위로 구성합니다.

| 모듈 | 책임 |
|---|---|
| `projects` | 프로젝트 생성·열기·이름 변경·삭제 |
| `editor` | 편집기 전체 화면 및 편집 도구 조합 |
| `canvas` | 슬라이드 캔버스, 좌표 변환, 요소 렌더링 |
| `slides` | 슬라이드 CRUD, 복제, 순서 변경 |
| `masters` | 마스터·레이아웃·테마 데이터와 UI |
| `elements` | 텍스트·이미지·도형·코드 요소 타입 및 렌더러 |
| `code-editor` | Monaco 편집 UI 및 코드 렌더링 연결 |
| `animations` | 애니메이션 설정 및 재생 순서 |
| `presentation` | 읽기 전용 발표 화면, 키보드 탐색 |
| `export` | JSON·PPTX·PDF 변환 및 다운로드 |

### Domain Layer

프로젝트·슬라이드·요소·테마의 타입과 순수한 비즈니스 규칙을 둡니다. React 컴포넌트, Zustand, IndexedDB에 직접 의존하지 않습니다.

예시 책임:

- ID 생성과 요소 기본값 생성
- 슬라이드 복제 시 ID 재발급
- 레이어 순서 계산
- 프로젝트 데이터 검증
- 구버전 JSON 마이그레이션

### Infrastructure Layer

IndexedDB, 파일 다운로드, 브라우저 API, PPTX 생성 라이브러리 등 외부 구현체를 담당합니다.

## 4. 상태 관리 전략

Zustand 스토어는 성격에 따라 나눕니다.

| 스토어 | 관리 데이터 | 예시 |
|---|---|---|
| `projectStore` | 현재 프로젝트와 프로젝트 메타데이터 | 현재 프로젝트 ID, 저장 시각 |
| `editorStore` | 일시적인 편집 UI 상태 | 선택 요소, 활성 도구, 줌, 패널 상태 |
| `slideStore` 또는 project slice | 슬라이드 데이터 변경 | 요소 추가·삭제·이동·속성 변경 |
| `presentationStore` | 발표 모드 상태 | 현재 슬라이드, 애니메이션 단계 |

원칙:

- 저장할 데이터와 화면에서만 필요한 UI 상태를 구분합니다.
- 선택 상태, hover, 드래그 중 포인터 위치 등은 프로젝트 JSON에 저장하지 않습니다.
- 한 요소의 속성 변경은 해당 요소를 식별하는 명령 함수로 수행합니다.
- 무거운 에디터 인스턴스(Monaco 등)를 프로젝트 JSON이나 일반 Zustand 상태에 넣지 않습니다.
- Undo/Redo 도입 시 변경 명령 또는 상태 스냅샷 전략을 별도로 설계합니다.

## 5. 캔버스 렌더링

### 좌표계

- 논리 캔버스 크기: `1280 × 720`
- 요소의 `x`, `y`, `width`, `height`는 논리 캔버스 기준 CSS 픽셀 값입니다.
- 브라우저 화면 크기에 맞춰 캔버스 전체에 scale을 적용합니다.
- 포인터 입력은 화면 좌표에서 논리 캔버스 좌표로 변환한 뒤 요소에 반영합니다.
- 확대/축소 UI 값은 캔버스 표시 배율이며 프로젝트의 요소 좌표를 직접 변경하지 않습니다.

### 렌더링 계층

1. 캔버스 배경
2. 마스터 요소
3. 슬라이드 요소
4. 편집 전용 오버레이(선택 테두리, 핸들, 가이드, 그리드)

편집 오버레이는 저장·발표·내보내기 결과에 포함하지 않습니다.

### 요소 렌더러

각 요소 타입은 공통 `position`, `style`, `id`를 기반으로 렌더링합니다. 요소 종류별 차이는 개별 Renderer로 분리합니다.

```text
ElementRenderer
├── TextElementRenderer
├── ImageElementRenderer
├── ShapeElementRenderer
└── CodeElementRenderer
```

새 요소 타입을 추가할 때는 타입 정의, 기본값 생성, 렌더러, 속성 패널, 저장/복원, 발표, 내보내기 지원을 함께 확인합니다.

## 6. 마스터·레이아웃 적용 방식

- **Theme**: 색상 팔레트, 글꼴, 기본 텍스트 스타일을 정의합니다.
- **Master**: 여러 슬라이드에 공통으로 표시할 배경·로고·푸터 등의 요소를 정의합니다.
- **Layout**: 콘텐츠가 배치될 placeholder의 종류와 기본 위치를 정의합니다.
- **Slide**: 실제 제목·본문·이미지·코드 등 개별 콘텐츠를 저장합니다.

렌더링 시 Theme → Master → Layout placeholder → Slide content 순으로 적용합니다. 슬라이드가 placeholder를 사용하면 해당 placeholder의 기본 위치·스타일을 초기값으로 삼고 슬라이드의 사용자 지정 값으로 덮어쓸 수 있습니다.

## 7. 저장 및 자동 저장 흐름

```text
사용자 편집
   │
   ▼
Zustand의 프로젝트 데이터 변경
   │
   ▼
변경 감지 / debounce
   │
   ▼
ProjectRepository.save(project)
   │
   ├── 프로젝트 메타데이터 저장
   └── 이미지 Blob 등 Asset 저장
   │
   ▼
저장 완료 상태 갱신
```

- UI는 `ProjectRepository` 인터페이스에만 의존합니다.
- 초기 구현체는 IndexedDB를 사용합니다.
- 자동 저장은 잦은 포인터 이벤트마다 실행하지 않고 변경을 묶어 처리합니다.
- 저장 실패 시 사용자에게 상태를 표시하고 재시도할 수 있어야 합니다.
- 삭제·가져오기 등 데이터 손실 가능성이 있는 작업은 확인 UX를 둡니다.

권장 인터페이스 예시:

```ts
export interface ProjectRepository {
  list(): Promise<ProjectSummary[]>;
  getById(id: string): Promise<PresentationProject | null>;
  save(project: PresentationProject): Promise<void>;
  delete(id: string): Promise<void>;
}
```

## 8. JSON 백업 및 복원

내부 프로젝트 데이터와 외부 백업 파일을 구분합니다.

- 내부 데이터: 프로젝트 JSON + IndexedDB에 저장된 바이너리 Asset
- 백업 파일: 프로젝트 데이터와 필요한 Asset 데이터를 함께 포함하는 교환 포맷
- 가져오기: 포맷 식별 → 버전 확인 → 데이터 검증 → 마이그레이션 → Asset 복원 → 프로젝트 저장

백업 포맷의 세부 구조는 `DATA_MODEL.md`를 기준으로 합니다. 큰 이미지가 포함되면 JSON 단독 파일의 크기가 커질 수 있으므로 ZIP 패키지 전환을 검토합니다.

## 9. 내보내기 아키텍처

내보내기는 편집기 상태를 직접 읽거나 수정하지 않는 별도 서비스로 구현합니다.

```ts
export interface PresentationExporter {
  export(project: PresentationProject, options?: ExportOptions): Promise<Blob>;
}
```

- JSON Exporter: 데이터 검증·직렬화·Asset 번들링
- PPTX Exporter: 요소별 PPTX 도형/텍스트/이미지로 변환
- PDF Exporter: 브라우저 출력 또는 PDF 생성 라이브러리 기반 변환

내보내기에서 모든 요소를 원본과 완벽히 동일하게 표현할 수 있다고 가정하지 않습니다. 코드 블록이나 복잡한 효과는 이미지로 대체할 수 있으며, 대체 여부와 품질을 테스트합니다.

## 10. 오류 처리 및 데이터 안정성

- 가져온 JSON은 사용 전에 스키마와 필수 필드를 검증합니다.
- 알 수 없는 요소 타입은 전체 프로젝트 로드를 중단시키기보다 오류 표시용 대체 요소로 처리하는 방안을 검토합니다.
- 스키마 버전이 더 높은 파일은 현재 버전에서 열 수 없음을 안내합니다.
- IndexedDB 사용 불가 또는 용량 초과 시 저장 실패를 명확히 표시합니다.
- 이미지 MIME 타입·크기·해상도 제한을 검토하고 유효하지 않은 파일을 거부합니다.

## 11. 향후 서버 확장

서버 기능이 필요해지면 다음과 같이 확장할 수 있습니다.

```text
React Client
   │ HTTPS REST API
   ▼
Spring Boot API
   ├── 인증/인가
   ├── 프로젝트 메타데이터 ── MySQL
   └── 파일 메타데이터 및 업로드 ── 로컬 스토리지
```

Local-first 구조를 유지하면서 `ProjectRepository` 구현체를 API 기반으로 추가합니다. 서버 도입 시에도 현재 데이터 모델을 기준으로 API DTO와 DB 모델을 설계하되, 브라우저 전용 필드는 서버에 저장하지 않습니다.
